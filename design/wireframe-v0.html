Govenr — the DAO's memory, on Platform.

A sketch for an open-source governance app on Dash Platform. Two chains, two jobs: L1 records the vote; Platform remembers why. Proposal hub reading the chain, discussion and reviews as data contracts, and DASH tips on the analysis that helps the DAO decide.

Lineage, with respect: DashCentral carried this DAO's governance for years — and when it went down, the votes survived on-chain while the reasoning was lost. This sketch is the successor, on rails that can't be lost. Credit to Rango and that service is the opening paragraph of whatever this becomes, not a footnote.
L1 CHAIN — TRUTH

The vote, read-only

Proposals, tallies, finalization — mirrored from the chain via DAPI, refreshed every block. The app never re-implements governance; the chain stays the sole authority on what passed.

PLATFORM — MEANING

The reasoning, as documents

Proposal content, discussion, and reviews as data contracts — decentralized, queryable, owned by the DAO. The layer that currently lives on whichever hosted site survives.

DASH — SIGNAL

The analysis, priced

Direct DASH tips on reviews and comments, with public on-chain receipts. The community rewards the analysis that actually helped it decide.

03

Deliberately not in v1

Sketch-level only — included so the feedback conversation can range over the whole idea, not just the first build.

LATER · v1.1

Verified-MNO badges

Operator-key attestation linking a masternode to a DPNS identity — proof that "this reviewer controls that masternode." A two-chain artifact by definition: can't exist on either chain alone.

LATER · v1.2

Vote analytics

Participation over time, cluster views, per-proposal whale maps — from public L1 records. The spreadsheet work, public and permanent.

LATER · v2

Proposal drafting

Draft with community feedback before the 5 DASH fee and the on-chain submission — cheaper decisions, better proposals, wallet-handoff only.

MAYBE · v5 era

Non-binding staked polls

When Platform 5.0 brings smart contracts and provable randomness: sentiment votes with DASH at stake — complementing, never replacing, L1 governance.

04

The data layer

Three small contracts plus tip receipts. Same patterns as the quiz contract — identity-bound, client-verified, one unique index each.

proposalContent + comment
{
  $ownerId, proposalHash,     // links to the L1 object
  body: markdown, milestones: [...],
  reports: [{ cycle, docId }]   // delivery reports, attached
}
// comment: { $ownerId, proposalHash,
//   body, parentId }  — one thread per proposal.
proposalReview + tip receipt
{
  $ownerId, proposalHash,
  stance: "support|concern|neutral",
  body: reasoning,
  mnoVerified: false             // v1.1 flips this true
}
// tip: { fromId, toId, docRef,
//   amountDash, txid }  — public receipts.

What this sketch is asking — before anything is built

  1. Would this get used? For masternode owners especially: would this become part of your voting routine, or one more tab that never opens?
  2. What's missing? What would this need to have — from anyone who's watched governance happen these last years — that isn't drawn here?
  3. What's the pain you'd fix first? If you could change one thing about how the DAO discusses and decides, what would it be?

This is an exploring-stage sketch — nothing is built, nothing is formal, no proposal is drafted. The direction traces back to a public ask for an open-source governance platform on Platform, and the person who asked it should be the first to disagree with this scope.

The chain records the vote. The platform remembers why. And the community — for the first time — prices its own analysis.
